# C-04a-002 · Login and activation pages

## Goal
`/login` and `/activate` work end to end on the real API, with `next` handling, refresh-once behaviour and no token exposure.

## Context
SPEC-04a §3.3 (login, logout, `next` safe-check, `/activate`), §3.4 login-specific messages, §5 Token. Use `@runway/client` (`login/logout/refresh/me`, `client.typed.POST('/auth/activate')`); do not rewrite refresh. Fields: label + `autocomplete` (`username`, `current-password`, `new-password`), email trimmed. Do not edit `src/app|ui|lib`, `package.json` — need it → stop and tell 001's owner.

## Scope
In: `src/features/auth/**` (pages, `safeNext()` + unit test, replace the 001 stubs `routes.tsx`/`nav.ts` content). Out: shell, other features.

## Steps
1. `safeNext`: accept only a single leading `/`, reject `//`, scheme, backslash. 2. Login page + already-logged-in redirect + 401/403/429 messages. 3. Logout action for the chip (exposed via the registry contract set by 001). 4. `/activate`: token read then `history.replaceState`; two password fields; 204 → "Đã kích hoạt" + Đăng nhập; 400/missing → expiry message. 5. No `console.*`, no storage.

## Tests
`safeNext.test.ts` → open-redirect regression (`//evil.com`, `https://x`, `javascript:`, `/\evil`). AC-2..AC-5 are proven at PROOF by the human checklist.
